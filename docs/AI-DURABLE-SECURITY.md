# Sinda durable persistence and host security (Preview)

## Database connection contract

The repository layer accepts a host-injected adapter exposing `query(sql, params)` and `execute(sql, params)`. Existing PostgreSQL pool and SQLite prepared-statement adapters must implement both methods. No driver, URL, username, password, or live database is bundled. Configure PostgreSQL with a dedicated role limited to the required tables and operations; do not use a superuser. SQLite must be opened by the host with filesystem permissions restricted to the application service account.

Run `migrateDurableStores({ adapter, dialect })` during a controlled startup/migration step. The schema creates project memory and approval tables plus indexes. Back up the database before migration and verify restore before enabling persistent use.

## Durable repositories

`PersistentProjectMemory` scopes every read by project ID and parameterizes values. `PersistentApprovalLedger` stores requester, approver/rejector/consumer, reason, target, timestamps, and state. Approval transitions use conditional updates so stale/replayed transitions fail. The host must enforce that approver identity comes from authenticated session claims, never model output or request body fields.

## Host handlers and RBAC

Use `createAuthorizedHostHandlers` to wrap the host's read/test/evaluate/analyze functions, then pass its returned handler map to `createWorkspaceTaskExecutor({ workspaceWriter, handlers })` before injecting that executor into `createSindaAI`. Every call requires a non-empty authenticated actor and project ID, then calls the host authorization function with actor, project, action, and resource. Missing/false authorization denies by default. The host remains responsible for authenticating the principal and implementing role membership and project ownership checks. Never trust actor IDs generated by the model.

## Prompt-injection boundary

Project memory, file contents, task descriptions, and tool outputs are untrusted data. `createUntrustedContextEnvelope` labels retrieved project context as data and serializes it separately from the system policy. This reduces accidental instruction mixing but is not a complete prompt-injection defense: the host must not expose secrets or privileged tools to the model, must independently authorize every tool call, validate structured outputs, and require human approval for privileged actions. Red-team tests in this PR verify that hostile strings cannot create handlers or permissions in the host adapter. They do not prove that a model can never be manipulated.

## Limits and rollout

- No live PostgreSQL or SQLite endpoint has been provisioned by this code change.
- No credentials are committed; connection configuration remains host-owned.
- Run migration in staging, then integration tests against disposable PostgreSQL and SQLite databases before connecting real project data.
- Keep all privileged actions disabled until authentication, RBAC, isolation, audit retention, backups, and independent security review pass.
- No merge, production deployment, or permission expansion is authorized by this preview work.
